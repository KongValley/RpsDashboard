# A股 RPS 看板

基于**欧奈尔相对价格强度（RPS, Relative Price Strength）**的 A 股选股与研究看板。

RPS 把全市场个股按区间涨幅做**横截面百分位排名**：RPS=90 表示这只票跑赢了全市场 90% 的股票。
欧奈尔在《笑傲股市》中指出，历年表现最好的股票在启动主升浪**之前**，RPS 就已经高于 80~90。

## 功能

| 模块 | 说明 |
|---|---|
| **RPS 排行榜** | 全市场 RPS15/20/60/120/250 排名，可按阈值、行业、成交额、ST 组合筛选，支持分页与**全量 CSV 导出** |
| **历史回看** | 所有页面均可选择任意历史交易日回看；非交易日自动**就近**回退到最近的有数据交易日 |
| **Δ名次** | 与 N 个交易日前的名次对比，看「这只票是最近在走强还是掉队」 |
| **板块强弱** | **证监会行业 / 概念题材**两套口径，等权涨幅的横截面 RPS + 领涨股 + 行业×周期热力图（**行按当前周期独立排序**） |
| **个股详情** | 单只股票的多周期 RPS 曲线 vs 后复权价格双轴图、跑赢全市场分位、所属行业强弱 |
| **策略回测** | 净值 vs 沪深300、风险指标、**RPS 分档前瞻收益**（自动解读单调方向）、**大盘择时**、**交易成本**、**涨跌停可交易性**；可选 **Top-N 选股**与**多因子合成分**信号源 |
| **因子研究** | 13 个价量/板块因子的**全样本 IC/IR、5 档分层收益、自相关、相关矩阵**（`cli factors` 落库 + 页面只读）；合成分（方向取自滚动训练窗的 IC 符号）可直接当回测与模拟盘的信号源 |
| **自选预警** | 自选股池（行首 ☆ 即加入）+ 条件预警规则（RPS 阈值 / 三升底 / 涨停）与命中记录；命中可**手动**推送到微信 |
| **自建模拟盘** | 不连任何券商的撮合引擎：按回测口径出计划、按日 K 逐笔撮合、产出净值曲线与持仓；**不需要券商账号**，详见「自建模拟盘」 |
| **QMT 接入** | 迅投 miniQMT **只读 / 影子 / 券商模拟盘**：账户与持仓快照、交易计划、影子成交与成本校准；**没有实盘分支**，详见「QMT 交易接入」 |
| **性能监测** | 后端 ASGI 中间件逐请求计时（`x-perf-ms`）+ 前端上报，两端在同一接口里对照；详见「性能监测点」 |
| **一键更新** | 页面按钮触发后台线程串起「日K → 涨跌停 → 行业分类（仅空表）→ RPS → 形态 → 预警」，实时显示阶段与失败原因；命令行入口 `update.bat` |

## 技术栈

- **后端**：Python 3.12 · FastAPI · pandas · SQLite · eltdx（通达信行情协议，唯一数据源）
- **前端**：Vue 3 · Vite · ECharts · vue-router
- **数据源**：eltdx（通达信行情协议，TCP 直连，全市场 209 秒）——其余候选源已评估后删除

### 4. 已有库升级（拉取新版本后跑一次）

**只跑 `cli init` 不会补出新周期列**：三张表的 DDL 都是 `CREATE TABLE IF NOT EXISTS`，
对已存在的表什么都不做。因此 `init_db()` 里挂了一个幂等迁移
（`db.ensure_period_columns()`）：按 `config.PERIODS` 缺哪列补哪列，并重建
`rps_daily` 的覆盖索引（`CREATE INDEX IF NOT EXISTS` 不会更新同名旧索引，必须
先 drop），**只做 `ALTER TABLE ADD COLUMN`，不重建表、不动数据**。实测 1.45 GB 的库
**7 秒**完成。

```powershell
.venv\Scripts\python.exe -m rpsboard.cli init                  # 补列 + 重建索引，会打印新增了哪些列
.venv\Scripts\python.exe -m rpsboard.cli tradestatus           # 一次性：修长假误判（只写真正变化的行）
.venv\Scripts\python.exe -m rpsboard.cli compute-rps --full     # 给新列填值（必须全量，增量只补新交易日）
.venv\Scripts\python.exe -m rpsboard.cli concept --compute-only --full   # 概念表同理
.venv\Scripts\python.exe -m rpsboard.cli quality               # 复权因子异常检测（官方因子接口约 20 秒）
.venv\Scripts\python.exe -m rpsboard.cli price-limits --fill --workers 6  # 可选：后台续采涨跌停实测值
```

跑之前在迁移/重算前**停掉 8000 端口上的服务**：API 持有只读连接，迁移时容易被
`database is locked` 挡住。

前端构建产物是**内容哈希**命名的（`/assets/index-<hash>.js`），但 `index.html` 本身
没有 `Cache-Control`：重新构建后，已经打开着的页面可能仍在跑浏览器缓存里的旧包
（实测踩过一次：页面行为与代码不符，其实是在跑昨天的 bundle）。升级后若行为异常，
**先 Ctrl+F5 强制刷新**再排查。

## RPS 计算口径

```
ret_N(t) = close(t) / close(t - N) - 1
rps_N(t) = ret_N 在 t 日全部有效股票中的百分位排名 × 100     # 榜首 = 100
```

- **后复权价**计算（eltdx `bars.get(..., adjust="hfq")`），规避除权除息造成的假跌幅
- 周期：**15 / 20 / 60 / 120 / 250 日**（15 = 3 周短线；250 日即欧奈尔原定义的 52 周）
- **新股自动排除**：上市不足 N 日 → `shift(N)` 为 NaN → RPS 为 NaN
  （15 日周期是其中门槛最低的一档：上市满 16 个交易日的股票就会**首次进榜**，
  此前四周期全为 NaN 被丢弃）
- **停牌日没有 bar，因此没有行**；价格用前值填充，停牌期间的区间收益仍然照算。
  `tradestatus=0` 的语义是「这根 bar 之前缺了交易日（**复牌当天**）」：复牌日本身是
  真实成交日（有量、有涨跌），**照常参与排名**（实测 1,299 个复牌股票日，其中 987 个
  因此进入了 RPS）。停牌判定按**交易日**间隔，长假不算停牌 —— 历史实现按自然日判定，
  把 21 个长假后首个交易日整天误判成停牌 → 那 21 天没有任何 RPS，2026-10-13 已修
  （见 `cli tradestatus`）。`tradestatus` 只保留作数据质量标记，不再参与 RPS 掩码。
- **负偏移还原（自动）**：`offset < 0` 的股票先整列加回 `|offset|`（`matrix.negative_offsets`，
  取最新档位）。还原**不需要 scale** —— 比值里它被约掉。实测 5 只（000793 / 600076 /
  600136 / 600180 / 600734）不还原时每个周期有 900 ~ 1,270 行偏差 > 20pp（最大 1,640pp），
  而且它们能拿到 `rps = 100` —— 回测会把「原始价 +10%」当成「+85%」买进去。
  详见「复权因子异常」。
- **异常端点不进入收益率（自动剔除）**：还原后的端点价 `< 1 元`（门槛见
  `config.ANOMALY_MIN_PRICE`，环境变量 `RPSBOARD_ANOMALY_MIN_PRICE` 可调，0 = 只剔非正价）
  一律不算。两个理由：① 负分母会翻转比值符号、0 分母得 ±inf，而排名把 +inf 当成
  最大值（实测 600076 的 `ret120` 曾是 −12725%）；② 接近零的分母会把**正常的原始价涨幅
  放大成几百个百分点** —— 同一只股票在 2024-12-18 的 `ret60` 曾是 **+998%**，而它当天的
  原始价只涨了约 8%。区间收益只取决于两个端点，所以按端点剔除，不是「跨过异常日整段作废」；
  规则由 `matrix.build_close_matrix` 统一执行，RPS 与回测前瞻收益共用同一套端点。
  实测被剔除的端点：**49 行**（还原口径；恰好等于 1.00 元整的行保留）。
- **横截面不足 1,000 只股票的日期不落库**（`config.MIN_CROSS_SECTION`，环境变量
  `RPSBOARD_MIN_CROSS_SECTION` 可调）：百分位是相对强度，几十只股票里排第一不代表强。
  实测 433 个早期稀疏日期因此不产出 RPS（见「数据规模」），剩下的 **1,285 天**每天
  有 3,981 ~ 5,361 只股票参与排名。行业/概念复用**同一批日期**，三张表口径一致。
- **ST 默认剔除**，可在界面放开

### 界面口径说明（2026-10-14 修订）

- **排行榜排序与分页**：分页由**排序键本身**决定。`sort=rps|ret` 时能在 rps_daily
  的覆盖索引上先取 Top-N（快路径），其余排序键（成交额/收盘价/涨跌幅）必须先 JOIN
  再排序分页。历史实现让内层子查询固定带 `LIMIT`，于是非 rps 排序取到的是
  「索引扫描顺序那一批」——实测 `sort=amount&limit=200` 的集合里
  `MAX(rps15)=3.75`（全市场倒数 3.75%），页面与 CSV 导出互相矛盾。现在页面第 1 页
  与导出的前 N 行逐行一致（`tests/test_api.py` 里两者互相断言）。
  页面的「排序」控件给出 **RPS / 区间涨幅 / 当日涨跌 / 成交额 / 收盘价 × 降序/升序**，
  按 `sort` + `direction` 两个参数传给后端（`direction` 缺省时按排序键的默认方向：
  涨跌幅/收盘价默认**升序**，所以想直接看涨幅榜要选降序）；导出与页面同参，
  可以直接用 `?sort=amount&direction=desc` 这样的链接分享一个榜单。
- **`market_percentile`（个股页「跑赢全市场」）**：= 该周期 RPS ≤ 我的股票占比，
  即全市场第一显示 100.0%。旧实现算的是「≥ 我」的占比，语义正好反过来
  （第一名显示 0.0%）。某个周期为 NULL 时该字段返回 `null`，不再恒为 0.0。
- **`pattern_daily.strength`（三升底）**：= **第三根收盘 / 第一根开盘 − 1**（三根阳线的
  合计涨幅）。历史实现的分母误用了第三根自己的开盘，于是 strength 恒等于第三根的
  自身涨幅（系统性偏小）。`cli patterns` 重算后全量回填（实测逐值核对：
  随机抽 30 条与 `close(T)/open(T-2)-1` 完全一致）。
- **形态「是否仍然有效」**：只看**截至查询日**的 K 线最低价有没有跌破第一根的
  `base_low`。旧实现的历史查询会读到查询日之后的行情，实测 2026-06-24~30 窗口
  364 条命中里 196 条（54%）的有效性标记是用了未来数据的错值。
- **CSV 导出**：「代码」列写成 `="000001"` 形式，Excel 打开时前导零不会丢；纯文本
  消费方会看到这层公式包装。以 `= + - @` 开头的文本（股票名等）会被加上 `'` 前缀，
  防 CSV 公式注入。字段用 `csv.writer`（`QUOTE_MINIMAL` + CRLF）输出，名称里带
  逗号/引号也不会串列。

## 重要限制

- **采集需要联网**：唯一数据源 eltdx 走通达信行情协议 TCP 直连（不走网页接口），
  离线时只能看已有数据。
- **首次初始化较慢**：`cli backfill` 拉全市场约 5574 只 × 1300 根日 K，实测
  **222 秒**（800 根 / 8 线程）到 **425 秒**（1300 根 / 6 线程）；
  之后日常 `update` 仍是**全量刷新这 1300 根窗口**，约 7 分钟 —— 窗口滑动会重写
  边界日期，所以它每次都重取一遍（换来的是幂等与自愈：中断后重跑即可）。
- **本机单人工具、无鉴权**：接口不校验身份，默认只监听 `127.0.0.1`，**不要暴露到公网**。
- **一键脚本分平台**：Windows 用 `start.bat` / `update.bat`，Linux / macOS 用
  `./start.sh` / `./update.sh`。

### 唯一数据源：eltdx（通达信行情协议）—— TCP 直连，不走网页

```bash
.venv\Scripts\python.exe -m rpsboard.cli update     # 日K + 涨跌停 + RPS
```

> eltdx 已声明在依赖里（`eltdx>=3.2.3`，见 `pyproject.toml`），
> `uv pip install -e ".[dev]"` 会一起装上，无需单独安装。

2026-10-12 实测曾评估五个源，最终**只保留 eltdx**：

| 源 | 全市场耗时 | 反爬风险 | 处置 |
|---|---|---|---|
| **eltdx** | **209 秒** | 无（TCP 协议） | **唯一保留** |
| 腾讯 | 约 2 分钟 | 12 线程并发直接触发 `waf.tencent.com` 封禁 | 已删除 |
| baostock | 约 70 分钟 | 多进程并发登录返回 `10001001 用户未登录` | 已删除 |
| 本地 .day | 22 秒 | 无 | 已删除（不复权、数据滞后一月，eltdx 自带成交额） |
| akshare/东财 | — | 本机网络阻断 | 已删除 |

> **代价是没有退路了**。eltdx 接口若变更，需从 git 历史取回适配器：
> `git show <commit>:backend/rpsboard/sources/baostock_src.py`。
> 这个取舍是明确知道的，不是疏漏。

删掉的适配器连带清掉了一批**永远为空的字段**：akshare 快照（量比/总市值/流通市值）
与通达信不提供的换手率（实测 `daily_bar.turn` 非空行数 0 / 427 万）。
按「**宁可没有，不要恒为 `—` 的假数据**」的原则，这些列已从接口与界面移除，
`spot_snapshot` 表也一并移除。

**为什么是 eltdx**：走通达信行情协议 TCP 直连，不是网页爬虫，
因此**没有 IP 限流、没有 WAF、没有代理问题**，且单次 `bars.get` 的 count 上限 800
（约 3.3 年，足够 RPS250 预热）。

除日 K 外，还用同一协议提供：

| 能力 | 接口 | 实测耗时 |
|---|---|---|
| 涨跌停价 | `daily_price_limits(trade_date=)` | 31~35 秒 / 5580 条，**服务端无缓存** |
| 当日停牌 | `latest_suspended()` | 0.0 秒 |
| 板块清单 | `board_quotes()` | 79 秒 |
| 板块成分股 | `board_member_quotes(code)` | 3.7 秒 / 板块 |


数据源在 `backend/rpsboard/config.py` 的 `DATA_SOURCE` 指定；当前唯一实现是 eltdx
（其余适配器已删除，可从 git 历史取回）。

### 复权因子异常（`cli quality`）

后复权价 = 原始价 × scale + offset，而 **offset 可以是负数**。当原始价接近
「变换零点」（`-offset / scale`）时，后复权价会被压成极小值甚至**穿零**，
此时 `close(t)/close(t−N)` 的比值会被放大到失真 —— 这不是脏数据，是变换本身的
数学性质：实测 600076 的 `ret60 = +998%`，而它当天的原始价只涨了约 8%。

**2026-10-14 起这段口径已经自动处理**（两处都在 `matrix.build_close_matrix`，
RPS 与回测的前瞻收益共用同一个矩阵）：

1. **负偏移还原**（`matrix.negative_offsets`）：offset < 0 的股票整列加回 `|offset|`。
   还原**不需要 scale** —— `(p+r)/(q+r)` 里 scale 被约掉，加常数后序列与原始价成比例，
   比值就是真实涨幅。实测 5 只（000793 / 600076 / 600136 / 600180 / 600734）在还原前
   **每周期有 900 ~ 1,270 行偏差 > 20pp（最大 1,640pp）**，而且它们能拿到 `rps=100`
   —— 回测会把「原始价 +10%」当成「+85%」买进去。
2. **端点剔除**（`config.ANOMALY_MIN_PRICE`，默认 1 元）：低于门槛的端点视为无效、
   该区间收益为 NULL。区间收益只取决于两个端点，所以按端点剔除而不是「跨过异常日
   整段作废」。

`cli quality` 负责**把异常摆到台面上**（报告为主，不改数据）：

| source | kind | 判据（全部可复算） |
|---|---|---|
| internal | `hfq_jump` | 库内单日后复权收益超出任何板块的涨跌停上限，且不是上市前 5 日、不是复牌日 |
| internal | `tiny_price` / `nonpositive_price` | 库内 `0<close<1` / `close<=0` 的每一行 |
| internal | `no_limit_day` | 无涨跌幅限制日（上市前 5 个交易日 / 复牌日）—— 正常，信息性 |
| official | `factor_jump` | 官方复权因子相邻档位 `hfq_scale` 变化 > 30% —— **这就是除权/送转事件本身**，正常企业行为，信息性 |
| official | `negative_offset` | 负偏移档位，**且该股在库内价格确实被压低**（否则 789 只里绝大多数根本没受影响） |

实测一次全市场检测（2026-10-14，1300 根窗口）：**可疑跳变 114 处 / 极小价 385 行 /
非正价 29 行（7 只）/ 负偏移档位 17 处（5 只）/ 除权事件 8,875 处 / 无涨跌幅限制日
45 处**，官方因子接口整轮 5,574 只只需约 6 秒（75 只/批）。结果进 `adjust_event` 表，
`cli status` 显示一行汇总，`cli update` 末尾会自动刷新一遍。

```powershell
.venv\Scripts\python.exe -m rpsboard.cli quality              # 离线扫描 + 官方因子，写库
.venv\Scripts\python.exe -m rpsboard.cli quality --offline    # 只做离线扫描（不联网）
.venv\Scripts\python.exe -m rpsboard.cli quality --dry-run    # 只打印，不写库
```

> **仍未自动处理的**（如实列出，代价与方向都写清）：
> - **跨除权/送转日的区间收益**：那天之后的价格被复权因子重新缩放，收益里含送转成分。
>   按什么比例裁剪是**判断**而不是事实，自动处理会静默改变已公布的回测结论 ——
>   要按符号/日期排查就直接查 `adjust_event`（`factor_jump` 行）。
> - **复牌首日不设涨跌幅限制**：`tradestatus = 0` 的日子（实测 45 处，如 603007
>   2024-12-26 跌 34%）**没有**进回测的买入过滤。方向是保守的：把这类暴涨日当涨停
>   跳过，不会凭它们拿到假收益。
> - **幸存者偏差**：库内所有股票都来自「当前上市」清单，**0 只退市股**。数据源的
>   `delisted_bars` 只有**不复权**价（`adjust == none`），混进后复权序列会直接造出
>   假收益，所以退市股无法补齐 —— 回测结果因此偏乐观，页面已常驻标注。
>
> 门槛可用环境变量调保守一些（例如 `RPSBOARD_ANOMALY_MIN_PRICE=2.0`），
> 改完需要重跑一次 `cli compute-rps --full` 才会生效。

### 其它限制

- **不要用「超时后放弃的线程」测数据源速度**：被放弃的线程仍持有连接，
  会把后续查询一起拖死，产生"查询极慢"的假象。要测量就用独立进程单发探测。
- **回测存在幸存者偏差**：用当前证券池回溯历史，中途退市的股票缺失，结果偏乐观。
  回测页面已常驻标注，**不可直接用于实盘决策**。
- **仅供研究学习，不构成投资建议**。

## 回测结论（实测，务必先读）

在 **2021-06-24 ~ 2026-08-27（5.19 年，64 个调仓点 × 持有 20 个交易日，5574 只全市场）**
上跑「RPS60 达标即等权买入、持有 20 个交易日」（零成本、涨跌停过滤**全区间生效**）：

| 策略 | 总收益 | 年化 | 最大回撤 | 夏普 |
|---|---|---|---|---|
| RPS60 ≥ 80 | **−25.33%** | −5.47% | −55.39% | −1.50 |
| RPS60 ≥ 90 | −47.60% | −11.71% | −66.17% | −2.94 |
| 沪深300 基准 | −18.20% | −3.8% | — | — |

**零成本就已经亏钱，而且跑输基准**（−25.33% vs −18.20%）。窗口拉长到 5.19 年
（含 2021-2022 的下跌段）之后，上一版「小幅正收益」的结论变成明确的负结果 ——
这不是策略变差，是**数据与口径修正后本来该有的样子**（改动逐条列在下面的注里）。

分档前瞻收益（**592 万样本，单调向下，且顶部为负**）：

| RPS 档 | 样本 | 平均 20 日前瞻收益 | 上涨概率 |
|---|---|---|---|
| 90–100 | 593,180 | **−0.32%** | 40.8% |
| 80–90 | 591,957 | +0.53% | 44.9% |
| 70–80 | 591,886 | +0.81% | 46.8% |
| 50–70 | 1,183,885 | +1.08% | 49.1% |
| 0–50 | 2,958,658 | **+1.35%** | 49.9% |

**这不是 bug，是真实的短期反转效应**（样本百万级、单调性明确）。要正确理解：

- 欧奈尔的 RPS 是**选股工具**而非**买卖时点**，他用的是 **52 周（年）**相对强度，
  配合 CANSLIM 的基本面（C/A/N/S）与流动性（L）条件，且**只在强势市场做多**。
- 本项目回测是**纯价格**的 60 日 RPS、等权买入、20 日固定持有、
  **全年无择时、无止损、无基本面过滤**——两者不是同一个东西。
- 因此正确结论是：**60 日 RPS 在 20 日持有期上表现为反转，不宜单独作为买入信号**，
  而不是「RPS 无效」。想复现欧奈尔的思路，应改用 RPS250 窗口、
  加入市场择时（如仅在指数站上均线时开仓）与基本面过滤。

> 本节数字在 **2026-10-14 第五次重测**。这一轮改了五处口径，每一处都会动数字：
> ① **抓取窗口 800 → 1,300 根**：回测窗口从 39 个调仓点（3.2 年）扩到 **64 个（5.19 年）**，
> 覆盖 2021-2022 的下跌段（基准从 +11.30% 变 −18.20% 就是这个原因）；
> ② **横截面门槛 1,000 只股票**（`config.MIN_CROSS_SECTION`）：433 个稀疏日期不再产出
> RPS，回测也不再在「没有信号的日子」调仓；
> ③ **负偏移还原**（`matrix.negative_offsets`）：5 只股票的区间收益以前**整段失真**
> （每周期 900~1,270 行偏差 >20pp，最大 1,640pp），它们曾凭假涨幅占据 `rps=100` ——
> 这条对**上方分档**影响最大；
> ④ **异常端点剔除**（`config.ANOMALY_MIN_PRICE`，49 行端点）；
> ⑤ **调仓日与覆盖率分母只取有 RPS 的交易日**（不再被 1,734 个含稀疏延伸的日期污染）；
> ⑥ **涨跌停从「规则推算兜底」换成全量实测**（1,285/1,285 天）：实测按真实涨停价判定，
> 比推算**少剔**一批（`limit_up_filtered` 26,281 → **15,333**，推算会把部分无涨跌幅
> 限制的日子当成有限制），各档因此上移约 1.5 个百分点。
> 加上引擎侧的修正（年化按首末调仓点的**真实日期跨度**折算、`rebalance < hold`
> 不再重复计息、`period`/`hold` 入口夹取、成本说明按实际持仓中位数生成），
> 零成本口径从早期的 +5.92% 走到今天的 **−25.33%**：
> **方向变了，原因是数据与口径被修正到它本来的样子，而不是策略变差。**
> 历史版本（+5.48% → +5.49%）的痕迹保留在 git 历史里。

**多周期共振口径**：回测页勾选「多周期共振」后，入池条件是「除所选周期外的
**全部**周期同时 ≥ 阈值」。周期清单直接取自 `config.PERIODS`，因此 **15 日短线
也在共振判定里**，新增周期会自动进入共振，不需要改代码（`analytics/backtest.py`
的 `resonance_mask()`）。

回测页面会自动识别单调方向并给出上述解读，不会把负面结果藏起来。

### 多因子合成分 · Top-N 选股（2026-10-15 新增，同一窗口实测）

同一窗口、同一持有期（60/20）、零成本与含成本各跑一遍。**`--select-top` 与
`--threshold` 是叠加关系**：阈值 0 = 全池前 N 只。

| 策略 | 总收益（零成本） | 总收益（含成本） | 年化（含成本） | 最大回撤（含成本） | 夏普 |
|---|---|---|---|---|---|
| RPS60 ≥ 80 **全市场**等权（现状） | −25.33% | **−63.15%** | −17.49% | −70.59% | −4.80 |
| RPS 打分 **Top-20** 等权 | −94.02% | **−94.84%** | −43.52% | −95.07% | −9.41 |
| **合成分 Top-20** 等权 | +37.36% | **+19.67%** | +3.57% | −31.18% | 0.88 |

三件事值得单独说：

1. **RPS 的「前 20 名」比全市场更差**（−63%→−95%）。这不是新 bug：上一节的分档表
   已经给出机理——**RPS 最高档的 20 日前瞻收益最低（−0.32%）**，所以只买最靠前的
   20 只，等于把这个反转效应集中下注。单因子 RPS 在任何一种选股方式下都不是好信号。
2. **合成分 Top-20 转正**（含成本 +19.67%）不是「调出来的」：因子方向由**滚动训练窗的
   IC 符号**决定（窗口整体落在 `t-hold` 之前，零幅度拟合），权重等权，**这一轮没有为了
   好看回头改因子池或权重**。它转正的直接原因是**方向反转**——11 个因子的全样本 IC
   全是负的（下表），于是合成后买的是「低波动 / 低振幅 / 低成交额 / 弱动量」那一侧，
   即**反转策略**，与分档表的反转向下完全一致。
3. 合成分的分档（零成本，五档）：+1.24% / +1.34% / +1.42% / +1.37% / **+0.74%**——
   顶部四档基本持平、最低档明显更低，是**弱正向**而非强单调；Top-20 拿到的收益
   更多来自「只持有分数最高的那一小撮」，而不是整条曲线的斜率。

因子评估台（`cli factors`，全样本研究口径）：

| 因子 | IC 均值 | IC_IR | 胜率 | 样本 | 自相关 |
|---|---|---|---|---|---|
| amt20（20 日平均成交额） | −0.1165 | −0.76 | 22.1% | 1,280 | 0.999 |

**11 个可用因子的 IC 全为负、胜率全部低于 50%** —— 这正是上表「反转」二字的来源，
也解释了为什么「按 RPS 排在最前」是最差的选法。`age` 与 `triple` 在本库上退化为
全 NaN（当天超过半数股票同值 → MAD = 0），见「未完成项」一节的说明。

相关矩阵里三对 `|corr| ≥ 0.7` 的是：`vol20 × amp20 = 0.92`、`bias20 × rev20 = 0.82`、
`bias20 × rev5 = 0.72` —— 合成时它们其实在重复押同一个注（等权合成没有去重，
这是已知取舍）。`ind_rps × mom = 0.37` 说明行业 RPS 与个股动量确实不是同一件事。

**必须一起读的边界**：① 幸存者偏差（当前证券池回溯，20 只持仓的集中度会放大它）；
② 窗口只有 5.19 年、64 个调仓点，一个反转风格的两三年就能解释大部分差异；
③ 成本已按**实际持仓只数**计（20 只时时最低佣金 5 元摊到每只 0.005%，比千只组合更重），
所以 +19.67% 不是「成本口径放宽」换来的；④ 因子清单与等权方案是**这一轮选的**
（研究者自由度），方向与权重没有拟合，但清单本身就是选择。
**结论按「三组数字并排记录」处理，不预设方向，也不为了让合成分好看而回头调参。**

### 自建模拟盘的三组对照（2026-10-15 实测）

同一区间（2026-06-01 ~ 2026-10-14，91 个交易日，100 万初始资金，`trade run --max-positions 20`）：

| 信号源 | 期末权益 | 收益 | 最大回撤 | 期末持仓 | 计划/委托/成交 | 累计费用 |
|---|---|---|---|---|---|---|
| 合成分 | 967,924 | **−3.21%** | 11.21% | 20 只 | 5 / 179 / 176 | 7,509 |
| RPS（对照） | 755,396 | **−24.46%** | 43.20% | 22 只 | 5 / 133 / 126 | 4,076 |

模拟盘是**逐笔撮合**出来的（限价挂不进去就不成交、涨停买不进、停牌顺延、最低佣金与
印花税逐笔计），与回测的「按前瞻收益复利」不是同一套算法，所以两者的绝对数字不可比；
可比的是**方向与相对关系**：这 91 天里合成分明显优于 RPS，与回测的结论一致。
「期末持仓 22 只 > max_positions 20」是撮合侧的既有事实（未成交的买单不会立刻补），
已在上一轮用 `liquidate_orphans` 收口，不再是「只进不出」的滚雪球。

**成本口径**（`backend/rpsboard/analytics/costs.py`）：

| 项 | 费率 | 方向 |
|---|---|---|
| 佣金 | 0.025%，**单笔最低 5 元** | 买 + 卖 |
| 印花税 | 2023-08-28 前 0.1%，之后 0.05% | 仅卖 |
| 过户费 | 0.001% | 买 + 卖 |
| 滑点 | 0.05% | 买 + 卖 |

**最容易被低估的是最低佣金**：等权分散持有上千只时，100 万本金摊到每只
才 1000 元，按比例算佣金只有 0.25 元，但券商按 5 元起收——**实际费率是名义值的 20 倍**。
成本因此按「组合名义金额 × 实际持仓只数」逐笔计算，而不是套一个常数比例。
本机实测这一次回测（RPS60 ≥ 80 / 持有 20 日）的**持仓数中位数是 1016 只**，
页面 `params.cost.assume_positions` 就是用这个实测值生成的（不再固定写 50 只）。

**分档前瞻收益那张图仍然不含成本**：它衡量的是「RPS 信号本身有没有预测力」，
混进执行摩擦会把信号质量与交易成本两件事搅在一起。页面已显式标注两者口径不同。

### 真实可交易性：涨停买不进、跌停卖不掉

| 情形 | 处理 |
|---|---|
| 买入日涨停 | 从当日候选池**剔除**（涨停买不进） |
| 卖出日跌停 / 停牌 | 该持仓收益**顺延**到下一可卖出调仓点（保守，可能低估回撤） |

实测一次完整回测（RPS60 ≥ 80 / 持有 20 日 / 含成本）有 **384 个持仓**触发顺延，
占 **36,188 个持仓的 1.06%**（2026-10-14 重测）。这个数比上一版（0.38%）大是**好事**：
以前只在实测覆盖的 128 天上判得出跌停，其余 760 天**整段不判**，现在全区间都判。

**涨跌停判定必须比「收益率」而不是「价格」**：`daily_bar.close` 存的是**后复权**价，
而 eltdx 的 `limit_up_price` 基于**不复权**前收盘价。直接比会算出当日 4303 家
「涨停」（占全市场 77%）；改比 `close(t)/close(t-1)-1` 与 `limit_ratio_pct` 后，
得到 8 涨停 / 14 跌停，符合 A 股实况。容差 0.2 个百分点，用于吸收交易所
价位四舍五入与后复权比率之间的偏差。

**数据来源分两层（实测优先，规则兜底）**：

| 层 | 来源 | 覆盖 |
|---|---|---|
| 实测 | `price_limit_daily`（eltdx `daily_price_limits`，含交易所公布的规则标签） | **1,285/1,285** 个 RPS 交易日全覆盖（表内共 1,734 天 / 968 万行，2026-10-14 补完） |
| 推算 | 板块规则：主板（含 ST，2024 新规后 ST 也是 10%）10% / 创业板·科创板 20% / 科创板 CDR(689) 10% / 北交所 30% / **上市前 5 个交易日无限制** | 只作兜底（实测缺失时才用；当前无缺失） |

推算层**用已采集的 135 个交易日、743,959 行逐行校验过：比例完全一致（0 处不一致）**，
新股前 5 日的 508 行也全部落在「无涨跌幅限制」。两层合并后回测对**每一天**都做过滤，
`warnings` 里会写明当次用的覆盖天数与一致率 —— 而不是像以前那样在未覆盖的日子
静默地少一层过滤。实测数据来自交易所口径（六种规则标签：主板 / 创业板 / 科创板 /
北交所 / ST / 新股前五日无限制），实测永远优先于推算。

> **采集成本与并发**：该接口**服务端不缓存**，每交易日一次调用（本机实测 31~239 秒，
> 与时段/服务端负载有关）。819 个未覆盖交易日按 35 秒/天串行要 8 小时；
> `--workers 6` 实测 6 天 186 秒（≈31 秒/天，服务端按连接排队，**并发只快约 15%**），
> 因此全量补齐仍需约 7 小时 —— 用 `cli price-limits --fill --workers 6
> --max-minutes N` 分批续采（跳过已覆盖日期、可反复运行；`--workers` 默认 1，
> 不显式指定不会加大采集压力）。

### 大盘择时的实测影响（2026-10-14，零成本口径）

上面「全年满仓、无择时」的结论，加上择时后会变成什么样：

| 择时条件 | 总收益 | 年化 | 最大回撤 | 夏普 | 空仓调仓点 |
|---|---|---|---|---|---|
| 不择时（满仓） | −25.33% | −5.47% | −55.39% | −1.50 | 0 / 64 |
| 沪深300 > 200 日均线 | **+22.95%** | **+3.98%** | **−20.67%** | **1.53** | 38 / 65 |
| **沪深300 > 50 日均线** | **+24.79%** | **+4.28%** | −23.27% | **1.93** | 36 / 65 |
| 沪深300 > MA200 且 MA50 > MA200 | +2.15% | +0.40% | −23.23% | 0.19 | 42 / 65 |
| （同期沪深300 基准） | −18.20% | −3.8% | — | — | — |

结论这一次很干脆：**三档择时全都同时改善收益和回撤**（−25.33% → +2.15% ~ +24.79%，
回撤 −55% → −21% ~ −23%），而且都跑赢买入持有的基准（−18.20%）。
两档年线（MA200 / MA50）差别不大，**结合 MA200 趋势过滤反而最差**（+2.10%）——
它空仓最多（42/65），把反弹也一起躲掉了。和上一版（窗口只有 3.2 年、结论是
「只有 MA50 有效」）相比，这次的样本更长、也更有说服力。

> 「空仓调仓点」= 该点 `holdings == 0` 的个数（这些点照记净值，曲线上才看得出空仓期）。
> 带择时的四档有 65 个点、不择时的 64 个点，差异来自窗口起点那几天均线未成形时
> 「数据不足就不下注」的策略（不择时没有这个约束）。

择时逻辑已用无未来函数测试守住（`backend/tests/test_market_filter.py`）：
扰动 T 日之后的行情，T 日的开仓判定必须逐值不变。

### 行业分类从哪来

板块强弱页的「行业」用的是 `industry_map`，由 `cli industry-map` 写入：

```powershell
.venv\Scripts\python.exe -m rpsboard.cli industry-map                       # 表为空时写入
.venv\Scripts\python.exe -m rpsboard.cli industry-map --replace             # 重建
.venv\Scripts\python.exe -m rpsboard.cli industry-map --replace --from-csv 我的行业.csv
.venv\Scripts\python.exe -m rpsboard.cli industry-map --fill-missing        # 只补缺行业的股票
```

数据来源按优先级自动选择（本机 2026-10-13 实测）：

| 来源 | 状态 | 行业口径 |
|---|---|---|
| eltdx 具名行业板块（`一级行业`/`二级行业`/`三级行业`/`880行业`） | 本机四个分类**都是 0 个板块**：板块定义文件 `tdxzs.cfg`/`tdxzs3.cfg` 不在本地、服务器 `download_file` 也返回 0 字节 | `通达信<分类>`（有名字时用板块名） |
| `tdxhy.cfg`（服务器可下，5587 行 / 每票一条） | ✅ 可用 | `通达信行业代码`：键是层级代码（`X` + 2 位 = 一级，**30 组**），该文件**不含行业名称** |
| `--from-csv` 自带映射（`symbol,industry[,industry_cls]`） | ✅ 可用 | `外部导入`（在该列里给出你自己的口径名） |

- **默认不覆盖已有数据**：本机现有的 5224 行是「证监会行业分类」口径（83 个具名行业），
  要换口径只能显式 `--replace`。具名口径**不可复现**（原先那份来自已删除的一次性脚本，
  仓库里没有可复现的名称来源），所以换掉就找不回来了 —— 想保留就先导出成 CSV。
- **`--fill-missing` 是补缺口而不是换口径**：保留已有行，只用 `tdxhy.cfg` 给**缺行业**
  的股票补一行。实测从 356 只没有行业分类降到 **1 只**（补进来的 363 只绝大多数是北交所
  股票，具名口径没有覆盖到它们）。代价是行业表里**两套口径并存**：83 个具名行业
  + 24 个通达信层级代码，逐行的 `industry_cls` 标出来源，行业 RPS 会同时出现
  `C20木材加工` 和 `X32` 这类键。这是有意的取舍：宁可标签不统一，也不要 6% 的股票
  永远进不了板块 RPS；想统一口径就自己用 `--from-csv` 提供映射。
- 一只股票只归一个行业（多归属时取成员数最少的那个），避免同一只票的涨幅被重复计入多个行业。
- 空库（刚 clone）时 `cli update` 会自动补这一步，所以新机器的板块强弱页不会空着。

### 概念/题材板块

证监会行业只有 83 个，粒度太粗（`C39 计算机、通信…` 里塞了 619 只），
而 A 股实盘看的是概念。本项目另有一套概念板块 RPS：

- 采集：79 秒拿全部板块清单 + 3.7 秒/板块取成分股，全量约 **31 分钟**
- 规模：**267 个概念、46,590 条成分关系、覆盖 5,443 只股票**，概念 RPS **254,008 行**
- **只有 202 个概念有 RPS 数据**：主分组规则下，65 个概念的成员全被别的概念先「拿走」了
  （成员最多的几个是车联网 295 / 虚拟现实 272 / 智能穿戴 259）。顶栏与
  `/api/meta/status.quality.concept` 会显示 `概念 202/267`，所以这不是「数据没算」，
  而是这张映射表的口径决定的 —— 要全量多归属就得改映射（并在 README 里同步口径）。
- 计算：**完全复用行业 RPS 的向量化实现**，只换一份分组映射表

> 一只股票常同时属于多个概念（AI 算力 / CPO 共享个股）。为了让概念 RPS
> 仍然可比，每只票**只归入一个主分组**——否则同一只股票的涨幅会被重复计入
> 多个概念，成分数也会虚高。界面上概念与行业可一键切换，热力图的各周期
> 独立排序逻辑原样复用。

### 一键更新

页面上「更新数据」按钮触发的是**后台线程**，不是同步请求：

```
[按钮] → POST /api/admin/update      → 立即返回（不同步等待）
           ↓ 后台线程
          ① 拉日K      约 7 分钟（1300 根/只，全市场 5,574 只）
          ② 采涨跌停    约 35 秒
          ③ 重算 RPS    约 10 秒（增量）
          ④ 识别三升底   约 1 分钟
          ⑤ 评估预警规则
          ⑥ 复权异常扫描 约 20 秒（诊断，失败不阻断）
           ↓
[轮询] → GET /api/admin/update/status → 阶段 / 耗时 / 失败原因
```

早期实现是**同步**跑完整流程的，219 秒必然超时，而且会阻塞请求线程。
现在页面上能看到当前阶段（准备中 / 拉取日K / 采集涨跌停 / 补行业分类 /
重算 RPS / 识别三升底 / 评估预警规则 / 复权异常扫描），失败时**展示原始错误
原因**而不是只弹一个 alert。同一时刻只允许一个任务（避免两个 eltdx 连接池
同时打行情服务器）。

命令行等价入口：`update.bat` 或 `python -m rpsboard.cli update`。

## 性能基线（本机实测）


> 增量路径只补「晚于最后一个已算出的交易日」的日子。某个日期算不出任何行时
> （如窗口起点那几天只有 1 只股票、都不足 16 根前置 K 线，或长假后首日全市场被标成
> 停牌）不会推进水位线，因此数据不全的新交易日会在次日自动重试。
> **中间出现真正的空洞增量补不上，用 `--full`。**

**落库是全量重算的瓶颈（2026-10-13 实测）**。全量写 404 万行时按 `tottime` 排序：

| 阶段 | 改造前（394 万行，索引在线） | 改造后（404 万行，先删后建） |
|---|---|---|
| `executemany` 写入 | **91.0 s** | **78.7 s** |
| 建索引 / DELETE / DDL | ~1.5 s | ~9.5 s（其中 CREATE INDEX ≈ 8 s） |
| 读 daily_bar（`fetchall`） | 7.5 s | 6.5 s |
| commit | 4.3 s | 2.4 s |
| 周期数学（`rank` + 转 DataFrame） | ~3 s | ~3 s |

**结论要说清楚**：把覆盖索引从写入路径上摘下来，单行插入成本降了约 16%（23.1 µs → 19.5 µs），
但写完之后 `CREATE INDEX` 要补回约 8 秒，所以**净收益只有几秒（约 4%）**，不是数量级的提速。
真正确定拿到的收益是**删掉冗余的 `idx_rps_date`**：少维护一棵 81 MB 的 B 树，库文件
VACUUM 后从 1567 MB 降到 1430 MB，且 `executemany` 的 91 s → 78.7 s 里有一部分来自它。
其余时间仍在 IO 与 pandas 落库路径上，要再快只能减少写入量（例如只重写变化的日期）。
上表其余数字都是四周期（2026-10-12）时代的，做性能对比时注意口径 —— 15 日周期后
只重测了全量重算。

### 接口耗时（2026-10-14 重新实测）

口径：真实 HTTP 请求（**含 ASGI 开销**，`backend/tests/bench_api.py`），
数据规模 660 万行日K / 626 万行 RPS / 1,285 个交易日。

| 接口 | 耗时 | 备注 |
|---|---|---|
| `/api/meta/status` | **8 ms** | 质量块 300 秒 TTL 缓存之后；**未缓存时 2.1 ~ 3.4 s**（见下） |
| `/api/meta/periods` | < 10 ms | — |
| `/api/meta/industries` | 10 ms | 107 个行业键 |
| 排行榜（RPS 筛选 + 100 行） | **40 ~ 50 ms** | 走覆盖索引的有序区间 |
| 板块排行 / 热力图 | 10 ~ 30 ms | 一次算出整块矩阵 |
| 个股详情 / 曲线（250 天） | 10 ~ 30 ms | 详情多一个分位统计 |
| 回测（冷启动，含建矩阵） | **67 s** | 矩阵被缓存后改参数 ~25 s、同参数且数据未变（结果缓存）毫秒级 |

历史对照（四周期、404 万行 RPS 时代，**直接调用处理函数、剔除 ASGI 开销**）：
排行榜第 1 页 467 ms → 38 ms、状态接口 733 ms → 3.4 ms、板块/热力图 ~280 ms → 4 ms、
排行榜 + 成交额过滤（慢路径）705 ms → 424 ms。**数据量涨了 55% 之后排行榜仍在 50 ms
以内**，说明覆盖索引 + 延迟连接这两条改动是有效的。

三个关键改动：

1. **`COUNT(*)` 不能用来判空**。对 660 万行的 `daily_bar`，`COUNT(*)` 要 **290 ms**，
   而 `MAX(date)` / `SELECT 1 ... LIMIT 1` 都是 **0.0 ms**。原来每个请求都要付一次。
   （`/api/meta/status` 的质量块同理：`COUNT(DISTINCT date)` 在 343 万行 / 626 万行上
   各要 ~0.3 s，所以整块做了 **60 秒 TTL 缓存** —— 未缓存时该接口实测 2.12 s，
   而前端在轮询它。）
2. **延迟连接**：先在 `rps_daily` 上按 RPS 取 Top-N，再只对这 N 行做 JOIN。
3. **ST 过滤必须用 `NOT EXISTS`**，不能用 `symbol IN (SELECT ...)`：
   IN 子查询会让优化器放弃日期索引改走主键逐只查找，实测 72.4 ms → 4.9 ms。

### 回测

| 场景 | 四周期时代（404 万行 RPS / 800 根窗口） | 现在（626 万行 RPS / 1300 根窗口） |
|---|---|---|
| 冷启动（读库 + 建矩阵 + 算 RPS） | 33.7 s | **67 s** |
| 改一个参数（阈值/周期/持有期） | **1.4 s** | **~25 s**（矩阵在进程内缓存，只重算选股与净值） |
| 同参数且数据未变（结果缓存） | **1.8 ms** | 毫秒级（指纹含三张表的日期与库文件 mtime/size，所以 `--fill` 写库期间会自动重算） |

> 原计划「回测复用已落库的 RPS」实测**不成立**：`SELECT ... FROM rps_daily` 要读回
> 600 万行再 pivot，和从缓存矩阵重算一样贵。真正的收益来自**矩阵缓存 + 结果缓存**。
> 冷启动从 34 s 涨到 67 s 是「数据量翻倍 + 窗口 800 → 1300 根」的直接结果
> （矩阵是 1,734 × 5,574 的浮点表，读取与 pivot 本身就要几十秒）；要再快只能
> 缩小参与股票数（例如只对过滤后的候选池建矩阵）。

## 工程事故与修复（2026-10-14）

**现象**：`daily_bar` 从 435 万行掉到 1 万行，只剩 49 个日期。

**根因**（`sources/tdxnet_src.py: backfill_bars`）：写入是

```
DELETE FROM daily_bar WHERE symbol=? AND date=?   （435 万个 (股票,日期) 对）
conn.commit()                                      ← 删除已落盘
df.to_sql("daily_bar", ...)                        ← 插入还没提交
conn.commit()
```

两次提交之间是一个**真实的空窗**：这中间进程被杀 / 断电 / 磁盘满，数据库就停在
「已删未写」的状态，而且因为删除已经提交，**无法回滚**。当天是我看到这个中间态后
把任务杀掉的 —— 判断可以理解（现场看起来就是「数据正在被毁」），但正确做法是
先确认它是不是处在写事务里（例如看它自己的日志输出），而不是立刻 SIGKILL。

**修复**：改成**单事务分块 upsert** —— 先把本轮帧写进临时表 `_bars_stage`，
再按 symbol 分批 `INSERT OR REPLACE INTO daily_bar SELECT ... FROM _bars_stage`，
每批一次提交。这样：
① 任何时刻都不会出现「已删未写」（每批提交只是新增/覆盖若干股票）；
② 写锁不会被一条几分钟的长事务占住（实测旁路命令会直接 `database is locked`）；
③ 中途被杀只需重跑，已写入的批不受影响。
`(symbol, date)` 本来就是主键，所以 `INSERT OR REPLACE` 天然幂等 ——
**根本不需要先删**，顺带也保住了超出抓取窗口的早期历史。

同一病灶（`DELETE` 提交后才写）在 `rps.materialize`（全量分支）、
`patterns.materialize`、`cli._write_all`、`db.upsert_master` 各有一处，已全部改成
「删除与写入同一事务」。

**回归测试**：`backend/tests/test_backfill_write.py` 用 sqlite3 的 trace 回调把写入
路径执行过的 SQL 钉死 —— **不得对 `daily_bar` 发 DELETE**、必须走 upsert、
重跑不产生重复行、插入失败时旧行仍在（`upsert_master` / `_write_all` 各一条）。
这类「两次提交」的写法不会在功能测试里暴露，只能这样锁。

**恢复**：修好后全量重取，**222 秒**拿回 5574 只 / 427.8 万行（随后扩到 1300 根窗口）。
当时 `price_limit_daily`（约 300 万行、已经采了 4 小时）与 `rps_daily` 等派生表都没被波及。

## 未完成项与已知边界

- **多因子库的边界（2026-10-15 新增）**：13 个因子**全部由现有表推导**，不新增数据源。
  库里没有股本 / 财报（`security_master` 只有 symbol/name/exchange/ipo_date/is_st），
  所以市值 / PE / PB 这类基本面因子**不在范围内**；也**不做行业中性化**（那会把
  「行业 RPS」这个因子本身中性化掉，与它的初衷冲突）。其中 `age`（上市交易日数）与
  `triple`（三升底确认日）在现有数据上**退化为全 NaN**：一个横截面里超过半数的股票
  取同一个值（窗口起点统一 → 老股上市天数完全相同；形态当天命中数远少于半数）
  → MAD = 0 → 该行没有区分度、不参与合成（页面显示 `—`、样本 0，`cli factors` 照常
  打印整张表）。要救它们得换口径（例如按上市年份分桶），或从 `FACTOR_LABELS` 里摘掉；
  本轮按「显示真实情况、不假装有信号」处理。因子矩阵**不落库**
  （13 × 1285 × 5574 × 8B ≈ 750 MB），落库的只有评估结果（约 30 KB 的 JSON，
  `factor_eval` 表，页面只读最新一行）。
- **P3 · 交易日历覆盖**：`/api/meta/dates` 取自 `rps_daily`（不是 `trade_calendar`，
  后者已删除）。实测 RPS 覆盖 **1,285** 个交易日（`daily_bar` 有 1,734 个不同日期）：
  差的 449 天里 **433 天横截面不足 1,000 只股票**（`config.MIN_CROSS_SECTION`，
  2026-10-14 起不落库 —— 那些日子只有少数长期停牌股有 bar），其余是窗口起点
  （前置 K 线不足 15 根）。**都不是缺口**。同理越早的日期有值的周期越少：
  250 日周期要 250 根前置 K 线，现在从 2021-11-22 起有值。
- **抓取窗口固定为 1,300 根（≈5.2 年），不做 2021 年以前的历史 —— 已定，不再讨论**。
  理由：全历史（600000 有 6,405 根）会让 `daily_bar` 581 MB → ~2.8 GB、
  `rps_daily` 701 MB → ~3.4 GB，库直接进 8 GB 量级、全量重算从 220 秒涨到十几分钟，
  而换来的只是**更早的回测区间**（那段区间的横截面本来就不全、规律也不同）。
  要更长的回测就直接调 `RPSBOARD_BARS`，但记得同步重估磁盘与重算耗时。
- **P2 · 数据库体积**：**3.30 GB / 2,320 万行**（daily_bar 660 万 + rps_daily 626 万 +
  涨跌停 968 万 + 概念 25.4 万 + …）。2026-10-14 两次 `VACUUM`：3.46 GB → 3.30 GB
  （43 秒，`freelist_count` 归零，`quick_check` ok）。
  占用大头：`rps_daily` 701 MB、`price_limit_daily` 604 MB、`daily_bar` 581 MB，
  以及各自的索引（`idx_rps_date_period` 386 MB、两个主键索引 207 / 185 MB、
  `idx_bar_date` 149 MB）。
  **增长速率**：每个交易日约 **+1.9 MB**（涨跌停 0.75 + RPS 0.6 + 日K 0.5）≈ **500 MB/年**。
  **峰值要留 6~7 GB**：全量回填/全量重算时旧表与新数据在同一事务里共存，外加 WAL
  与 `_bars_stage` 临时表（实测 WAL 一度到 1.5 GB）；涨跌停续采一轮也让库从
  2.66 → 3.46 GB。
  **`open/high/low` 不能删**：三升底形态（`analytics/patterns.py`）、排行榜的形态失效价
  （`api/rps.py` 的 `pattern_state()` 按 `date <= 查询日` 聚合 `MIN(low)`）、个股页失效判定
  （`api/stock.py` 一次取全量 `(date, low)` 后用反向累计最小值，不再逐条查 `MIN()`）都在用；
  `volume` 被个股曲线用。继续瘦身只能走「历史裁剪」这类有损方案，本轮不动。
- **复权因子异常（剩余部分）**：负偏移股票的区间收益已**自动还原**
  （`matrix.negative_offsets` + `build_close_matrix`，实测 5 只、每周期
  900~1,270 行偏差 >20pp 的失真因此消除），端点价 `< 1 元`（含穿零）的区间收益也
  **自动剔除**（`config.ANOMALY_MIN_PRICE`）。仍未自动的是 **① 跨除权/送转日的收益**
  （收益里含送转成分，按什么比例裁剪是判断不是事实）**② 复牌首日不设涨跌幅限制**
  （实测 45 处，方向保守：当涨停跳过）**③ 退市股无法补齐**（数据源的 `delisted_bars`
  只有不复权价，混进来会造假收益）—— 三条都只报告，
  见「复权因子异常」。
- **涨跌停历史覆盖（2026-10-14 补完）**：`price_limit_daily` 现在覆盖**全部 1,734 个
  交易日 / 968 万行**（RPS 的 1,285 天 100% 实测，不再依赖推算）。
  采集口径：接口**服务端不缓存**、一次一天，实测 **1.5~6 分钟/天**
  （早期 31 秒/天是在 800 根窗口 + 机器空闲时测的）；本轮 1,071 天跑了 8.6 小时。
  单日失败（`database is locked`，并发写重算时会撞 30 秒超时）会由下次 `--fill`
  按「行数不足当日一半」自动挑回，**不需要手工修**。
  日常 `cli update` 只补最新那一天，所以后续维护成本是每天约 35 秒。
  **注意实测与推算的差别**：实测按**真实涨停价**判定，比规则推算**少剔**一批
  （最近一次回测 `limit_up_filtered` 26,281 → **15,333**）——推算层会把部分
  无涨跌幅限制的日子当成有限制，属于过度保守。

## 自选股池与条件预警

在「排行榜」点行首 ☆ 即加入自选，顶栏「自选预警」页可以增删自选、管理规则、
查看命中记录。命令行为等价入口（同样只落库 + 终端输出，**不做消息推送**）：

```powershell
.venv\Scripts\python.exe -m rpsboard.cli watch add 600519 --note 白马   # 加入自选
.venv\Scripts\python.exe -m rpsboard.cli watch ls                       # 自选 + 当日 RPS
.venv\Scripts\python.exe -m rpsboard.cli watch rm 600519

.venv\Scripts\python.exe -m rpsboard.cli alert add --name RPS90 --kind rps_threshold `
    --params '{"period":60,"min":90,"max":100}'
.venv\Scripts\python.exe -m rpsboard.cli alert ls                       # 规则 + 累计命中
.venv\Scripts\python.exe -m rpsboard.cli alert run                      # 评估并落库
```

规则类型（`kind` 决定 `params` 的 JSON 结构）：

| kind | params | 命中条件 |
|---|---|---|
| `rps_threshold` | `{"period":60,"min":90,"max":100}` | 当日 `rps{period}` 落在区间内 |
| `sanxingdi` | `{"window":5}` | 近 window 个交易日内出现过三升底 |
| `limit_up` | `{}` | 当日按 `limit_ratio` + 容差判为涨停 |

- 命中写进 `alert_hit`，主键 `(规则, 日期, 股票)` → **重复 run 幂等**（实测真实库
  533 条命中，连跑两次行数不变）。
- `cli update` 与页面「更新数据」的最后一步会自动跑一次 `alert run`，返回里带
  `alert_hits`。
- 数据结构：`watchlist(symbol, note, added_at)`、`alert_rule(id, name, kind, params,
  enabled, created_at)`、`alert_hit(rule_id, date, symbol, detail)`。这三张表是**全 API
  唯一的写入口**（`backend/rpsboard/api/watchlist.py`），其余 handler 仍只读 SQLite。
- 已有库升级后需要跑一次 `cli init` 建这三张表（脚本全是 `CREATE TABLE IF NOT
  EXISTS`，幂等、不动数据）。

## 自建模拟盘（mode=local）：不连任何券商

QMT 的**股票**模拟账户是券商提供的（客户端自带的 11 个「模拟」通道全是期货），
拿不到就没有交易对手。但 RPS 策略要验的东西 —— 限价挂不挂得进去、整手取整吃掉
多少、停牌顺延几次、最低佣金对小资金的惩罚 —— 用**库里已有的后复权日 K** 就能回答，
而且这份数据就是回测用的同一份，结论可以直接对照。

```powershell
# 在区间上逐日「出计划 → 次日撮合 → 盯市」
.venv\Scripts\python.exe -m rpsboard.cli trade run --from 2026-01-01 --cash 1000000 \
    --period 60 --threshold 80 --hold 20 --max-positions 20

.venv\Scripts\python.exe -m rpsboard.cli trade paper   # 打印净值与持仓
```

页面上「交易 → 自建模拟盘」有净值曲线与持仓明细。**不需要任何券商账号，
也不连 QMT**（参考价直接取库内 `daily_bar.close`）。

### 撮合规则（刻意保守，宁可少成交也不高估）

| 规则 | 内容 |
|---|---|
| 下单 | T 日收盘后按 `close(T) ∓0.5%` 生成**限价单**，T+1 日内撮合 |
| 成交 | 买单 `low(T+1) ≤ 限价`、卖单 `high(T+1) ≥ 限价` 才算挂进去，成交价取**限价本身** |
| 涨跌停 | 涨停日买不进、跌停日卖不掉（收益率比法，与 `analytics/limits.py` 同一条规则） |
| 停牌 | 当日无 bar 或 `tradestatus=0` → 订单**顺延**到下一交易日，不撤单 |
| 资金 | 现金/持仓不够时按**整手**缩减，全不够则拒单，绝不下成零股或透支 |
| 费用 | 逐笔走 `analytics/costs.py` 的 `CostModel`（佣金最低 5 元、印花税按日期分段、过户费、滑点） |
| 调仓 | 每 `hold` 个交易日重平衡一次；**掉出候选的持仓清仓**（否则组合只进不出） |
| 仓位 | 等权 `max_positions` 只；每期预算是**总权益 × 0.95**（现金 + 持仓市值，不是只有现金） |

### 实测（2026-10-15，100 万本金）

| 口径 | 结果 |
|---|---|
| 区间 | 2026-06-01 ~ 2026-10-14，91 个交易日，5 次调仓 |
| 委托 / 成交 | 133 笔 / 126 笔（7 笔限价未触及，0 笔被涨停或停牌顺延） |
| 期末 | 755,396 元（**−24.46%**），最大回撤 **43.20%**，期末持仓 22 只 |
| 累计费用 | 4,075.53 元（约本金的 0.41%） |

对照：同一策略的**零成本全市场等权**回测在完整 5.19 年窗口上是 **−25.33%**，
含成本 **−63.15%**。模拟盘的 −24.46% 与之同量级，且这里每一笔都是真实撮合出来的
（限价挂不上就真的没成交，费用逐笔扣），不是把前瞻收益乘进净值。

## QMT 交易接入（只读 / 影子 / 券商模拟盘）

接的是迅投 QMT 客户端的 **miniQMT** 交易接口（`xtquant`）。三档递进：

| 档 | 做什么 | 会发单吗 |
|---|---|---|
| **P1 只读** | `trade status` 拉账户与持仓、落 `position_snapshot`；交易页展示；halt 总开关 | 否 |
| **P2 影子** | `trade plan` 按**回测口径**生成交易计划；`trade shadow` 模拟成交并校准成本假设 | 否 |
| **P3 券商模拟盘** | `trade execute --plan-id N` 真发**限价单**到券商**模拟**账户 | 是 |

**没有实盘分支**：代码里不存在 `live` 模式，`TRADE_MODE` 只接受 `paper` / `local` /
`sim`（`local` 是自建模拟盘，不连券商），
且 `execute` 必须显式带 `--i-know-this-is-sim`。⚠️ **本项目无法识别客户端登的是
不是实盘资金账户**——若 QMT 客户端登的是实盘账户，误配会发出实盘单。
触发方式全部手动执行，**不引入守护进程或定时器**。

### 为什么要有子进程

`xtquant` 随客户端自带，且**只提供 cp36~cp311 的编译扩展**
（`xtpythonclient.pyd` / `IPythonApiClient.pyd`），而项目 venv 是 **Python 3.12**
→ 直接 `import xtquant.xttrader` 就是 ImportError。所以项目里只有一层知道这件事：

```
cli / api  →  broker/qmt.py  ──subprocess(一行 JSON)──▶  QMT_PYTHON(=3.11)
                                                          └─ rpsboard/broker/bridge.py
                                                             └─ 客户端 site-packages 里的 xtquant
```

桥只用标准库，那个 3.11 环境**不需要装任何包**；协议是 stdin/stdout 各一行 JSON，
xtquant 自己的日志被重定向到 stderr，断线事件也从 stderr 走
（`{"event":"disconnected"}`），绝不污染响应行。

### 配置

全部读 `RPSBOARD_*` 环境变量或仓库根 `.env.local`（已 gitignore）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `RPSBOARD_QMT_DIR` | `D:\software\QMT` | 客户端根目录 |
| `RPSBOARD_QMT_USERDATA_MINI` | `<QMT_DIR>\userdata_mini` | 传给 `XtQuantTrader` 的登录态目录 |
| `RPSBOARD_QMT_PYTHON` | 无（**用到 QMT 时必填**） | 跑桥的解释器，**ABI 必须与 .pyd 一致**。默认留空是刻意的：写死某个用户目录会把本机路径带进公开仓库。用 `uv venv --python 3.11 backend/.venv-qmt` 建一个空环境，再指到 `.venv-qmt\Scripts\python.exe` |
| `RPSBOARD_QMT_ACCOUNT` | 无（必填） | 资金账号。**凭据级**：日志、接口、页面一律只留后 4 位 |
| `RPSBOARD_TRADE_MODE` | `paper` | 只允许 `paper` / `local` / `sim`（`local` = 自建模拟盘，见上一节） |
| `RPSBOARD_TRADE_HALT_FILE` | `data/trade.halt` | halt 哨兵；存在即禁止一切发单 |

客户端必须**保持登录**（`userdata_mini` 的本地 IPC 就是行情与交易网关）。
`connect()` 返回非 0 即失败——官方接口不会自动重连，也没有自动重连。

### 命令

```powershell
# P1 只读
.venv\Scripts\python.exe -m rpsboard.cli trade status      # 账号/现金/持仓 → position_snapshot
.venv\Scripts\python.exe -m rpsboard.cli trade snapshot    # 只刷持仓快照

# P2 影子
.venv\Scripts\python.exe -m rpsboard.cli trade plan --period 60 --threshold 80 --hold 20 `
    --max-positions 20 --mode paper                         # --date 缺省 = rps_daily 最新日
.venv\Scripts\python.exe -m rpsboard.cli trade shadow --plan-id 1
.venv\Scripts\python.exe -m rpsboard.cli trade calibrate --days 20

# P3 券商模拟盘（**限价单**；市价单只在实盘生效，模拟环境不支持）
$env:RPSBOARD_TRADE_MODE = "sim"
.venv\Scripts\python.exe -m rpsboard.cli trade execute --plan-id 1 --i-know-this-is-sim
.venv\Scripts\python.exe -m rpsboard.cli trade reconcile   # 现持 vs 计划目标，有差异退出码 3
.venv\Scripts\python.exe -m rpsboard.cli trade halt --on    # 总开关；--off 解除
```

退出码：`0` 正常 / `2` 配置或连接失败 / `3` 有差异或有跳过项 / `4` 部分委托失败。

### 计划口径（与回测共用同一份选股代码）

`trade_plan` 的候选来自 `analytics.backtest.entry_mask` —— **回测与交易计划共用
同一个函数**，否则最先坏掉的是「回测显示买得进、计划却空手」这类没法排查的偏差。
在回测口径之上，计划额外做了三件事，并把偏差写进 `trade_plan.note`：

| 差异 | 说明 |
|---|---|
| 持仓数 | 回测是**全市场等权**（几百只）；计划只取前 `--max-positions` 只 |
| 委托价 | 回测按滑点率建模成交；计划用 **QMT 最新价 ∓0.5% 的限价**（保守） |
| 可交易性 | 逐票校验：停牌（`tradestatus=0`）、无实测涨跌停行、越界、取不到价、买不起一手 → 记 reason 并**跳过**（绝不推算一个猜的价位去下单） |

影子成交按**限价**全额成交，用来校准回测里的往返成本假设：
计划预埋的价格摩擦是 **0.5% × 2 = 1%**，而 `costs.CostModel` 的滑点只有
**0.05% × 2 = 0.1%**（其 1.14% 里另外含佣金/印花税/过户费）。
`trade calibrate` 把三栏并排打出来 —— 结论是**回测的滑点假设比计划实际预埋的乐观 10 倍**。

### 发单前的三道闸

1. **风控**（`broker/risk.py`）：halt 哨兵、`mode` 必须是 `sim`、交易时段
   09:35–11:30 / 13:00–14:57、现金占用 ≤ 95%、单票 ≤ 20% 预算、笔数 ≤ 60、
   换手 ≤ 4× 预算。**刻意没有绕过开关**（没有 `--force` / `--now`）。
   单笔金额 < 5000 元的票只剔除自身，其余照发。
2. **对账**：账户在建计划之后是否被外部动过（手工买卖等）。有差异整批拒绝，
   **不自动补单**。
3. **幂等**：`(trade_date, symbol, side, plan_id)` 唯一，重跑不会重复发单。

执行途中连接断开 → 计划标 `halted` 并（若已配置推送）推一条提醒。
委托/成交全程落库（`trade_order` / `trade_fill`），重跑对账安全。
